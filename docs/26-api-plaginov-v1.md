## Контекст

После этапа 0 функции (календарь, цели, разбор Inbox, Inbox) живут отдельными модулями. Они регистрируют себя в реестрах ядра. Но код функции по-прежнему импортирует внутренние модули ядра: `store.svelte.ts`, `layout.ts`, `journal.ts`, компоненты. Плагином в смысле брифа это ещё не является.

Этап 1 даёт три вещи:

1. **Публичный API** `@panopticon/api`. Это единственное, что видит плагин: типы и объект `ctx`. Встроенные плагины пишутся только на нём, это проверяет тест.
2. **Манифест и загрузчик.** Встроенные и сторонние плагины описываются одинаково. Сторонний плагин — это папка с `manifest.json` и `main.js`.
3. **Права и сеть.** Права из манифеста проверяются в API и в командах Rust. Прямая сеть из окна закрыта.

Поведение приложения для пользователя на этапе 1 не меняется, кроме нового раздела «Настройки → Плагины». Встроенные функции на этапе 1 ещё не переезжают на API, это этапы 2 и 3. Исключение — наборы тем (1.4).

## 1. Модель выполнения

- Код плагина выполняется в окне приложения как ES-модуль. Изоляции в v1 нет.
- API устроен так, будто между плагином и ядром граница, чтобы в v2 можно было перейти на iframe или Worker без переписывания плагинов:
  - каждый вызов `ctx` асинхронный или возвращает `Dispose`;
  - на вход и выход идут только данные: JSON, `HeadingRef`, `Date`. Объекты ядра (store, NoteFile, Tab, EditorView) наружу не выходят;
  - вид плагина получает DOM-элемент и рисует в нём сам: `render(el, state, tab) → Dispose`. Svelte от плагина не требуется;
  - общие механизмы ядра (форма, выбор даты, выбор места, разбор) — это вызовы, которые открывают интерфейс ядра и возвращают результат. Компонентов для вставки API не даёт.
- Права защищают от ошибок, а не от злого умысла. Это сказано пользователю при включении стороннего плагина (п. 7.2).
- Ошибку плагина ядро ловит, и плагин выключается до перезапуска. От зависания (бесконечного цикла) v1 не защищает: это записано в «Чего нет в v1».

## 2. Устройство кода

- `src/api/` — пакет API: `index.ts` (типы, `definePlugin`), `ctx.ts` (сборка `ctx` для плагина), `manifest.ts` (разбор и проверка манифеста). В сборке и тестах он доступен по имени `@panopticon/api` через alias в `vite.config.ts` и `paths` в `tsconfig.json`.
- `src/plugins/<id>/` — встроенные плагины: `manifest.json`, `main.ts`, свои компоненты и тесты.
- **Граница проверяется тестом.** Vitest-тест `src/plugins/boundary.test.ts` читает исходники `src/plugins/**` и падает, если файл импортирует что-то кроме `@panopticon/api`, своих файлов плагина, `svelte` и `svelte/*`. ESLint в проекте нет, и ради одного правила он не нужен.
- Службы ядра (из 0.2, перенесено в 1.1) делаются ровно в том объёме, который нужен `ctx`:
  - файлы и запись;
  - индекс;
  - оболочка (реестры);
  - настройки и хранилища;
  - клавиши.

  Это фасады над `store`, не переписывание. `store.svelte.ts` целиком не режем.

## 3. Манифест

```json
{
  "id": "hello",
  "name": "Привет",
  "version": "1.0.0",
  "description": "Пример плагина",
  "author": "Yury Bogdanov",
  "api": "^1.0",
  "minAppVersion": "1.0.0",
  "main": "main.js",
  "styles": "styles.css",
  "permissions": ["index.read", "files.edit", "clipboard"],
  "net": [],
  "contributes": {
    "commands": [{ "id": "hello.greet", "title": "Привет: поздороваться", "keys": ["⌃⌘H"], "group": "hello" }],
    "navSections": [{ "id": "hello", "title": "Привет", "icon": "M4 10h12", "key": "hello.show" }],
    "views": [{ "id": "hello.board", "title": "Доска", "icon": "M4 4h12v12H4z" }],
    "settings": [{ "section": "Привет", "icon": "M4 10h12", "groups": [] }],
    "statusSets": [{ "name": "Привет", "states": "IDEA DOING | DONE" }],
    "themes": []
  }
}
```

**Поля:**

- `id`: `[a-z0-9-]`, до 64 символов, уникален. Совпадает с именем папки и с файлом хранилища `.orgnotes/plugins/<id>.json` из 0.6.
- `api`: диапазон semver. API v1 стартует как `1.0.0`. До контрольной точки M2 считаем его нестабильным: можем менять без мажора, сторонних плагинов ещё нет.
- `minAppVersion`: версия приложения. Этап 1 выходит в 1.0.0: плагины — повод для мажорной версии.
- `permissions`: подмножество `index.read`, `files.read`, `files.edit`, `clipboard`, `net`, `process` (п. 6).
- `net`: хосты для `net.fetch`, например `"jira.company.ru"` или `"*.company.ru"`. Используется только с правом `net`.
- `contributes`: всё, что можно объявить данными. Ядро регистрирует это **до загрузки кода**:
  - команды появляются в палитре и в «Клавишах», а конфликты сочетаний видны, даже если плагин выключен;
  - раздел навигатора показывается кнопкой;
  - настройки рисуются по схеме.

  Код подключает к объявленному поведение.
- `commands[].keys`: сочетания по умолчанию, в формате `keys.ts`. Запрещены ⌘S, ⌘W, ⌘Q, ⌘, и ⌘Z (п. 6.3). С запрещённым сочетанием команда регистрируется без него, а в списке плагинов видно предупреждение.
- `settings`: схема из 0.6 в JSON-виде. Это `Group[]` с полями `choice`, `switch`, `text`, `file`, `pair`. Функций в манифесте нет, поэтому зависимые подсказки и списки вариантов плагин даёт кодом: `ctx.settings.dynamic(key, …)` (п. 5.7). Блок в чужом разделе — `{ "block": "Агенды", "groups": [...] }`.
- `statusSets`: наборы статусов в памяти (как «Цели на квартал» в 0.6). Существуют, пока плагин включён. В `config.json` не пишутся.
- `themes`: для плагина-данных (1.4). Это массив путей к JSON тем внутри папки плагина.

**Проверка.** Манифест разбирается `parseManifest(json) → { ok, manifest } | { ok: false, problems: string[] }`. Плагин с ошибками в манифесте в «Плагинах» виден, но включить его нельзя, причины показаны списком.

## 4. Жизненный цикл

1. **Поиск.**
   - Встроенные манифесты собираются при сборке: `import.meta.glob('src/plugins/*/manifest.json')`.
   - Сторонние ищет Rust: команда `list_plugins` читает `<app config dir>/plugins/*/manifest.json` (рядом с `themes/` из ТЗ 25).
2. **Проверка:** манифест, `api` и `minAppVersion`, совпадение `id` с папкой, отсутствие дубля `id`. Если встроенный и сторонний совпали по `id`, побеждает встроенный, сторонний показан с причиной.
3. **Регистрация объявленного** у включённых плагинов: команды, клавиши, разделы, виды, настройки, наборы статусов. У выключенных ничего не регистрируется. Их вкладки восстанавливаются заглушкой (п. 4.2).
4. **Загрузка кода** включённых плагинов, после первого рисования окна, чтобы не задерживать запуск:
   - встроенные — динамическим `import()`;
   - сторонние — `main.js` читает Rust (`read_plugin_file`, путь проверяется: только внутри папки плагина), окно подключает его как модуль из Blob. Поэтому `main.js` — один собранный модуль без импортов: `export default { activate(ctx) { … } }`; `@panopticon/api` нужен только для типов (уточнено в 1.2, вместо протокола `plugin://`);
   - `styles.css` подключается тегом `<link>`.
5. **Запуск:** `plugin.activate(ctx)` внутри обёртки, которая ловит ошибки.
6. **Выключение** — в «Плагинах» или после ошибки:
   - вызывается `deactivate()`;
   - ядро само снимает всё, что плагин зарегистрировал через `ctx`: обработчики, виды, подписки, стили. Явный `Dispose` плагину вызывать не обязательно;
   - вкладки плагина становятся заглушкой.
7. **«Перезагрузить плагины»** (команда палитры и кнопка в «Плагинах»): выключить всё, перечитать папку, включить заново. Нужна авторам плагинов.

### 4.1. Ошибки

- Под обёрткой выполняются `activate`, обработчики команд, `render` видов, обработчики событий и действия разбора.
- Брошенная ошибка или отклонённый промис выключает плагин до перезапуска. Пользователь видит уведомление «Плагин „Привет“ выключен: <сообщение>» с действием «Подробнее». В «Плагинах» записаны причина и стек.
- Выключение после ошибки действует до перезапуска. Включённым в настройках плагин остаётся, поэтому после перезапуска он снова загрузится.

### 4.2. Вкладки выключенного плагина

Такие вкладки уже есть: это заглушка «Функция выключена» из 0.3. На этапе 1 у неё появляются имя плагина и кнопка «Включить», если плагин можно включить. Раскладка не теряется.

## 5. `ctx` — объект API

```ts
export interface Plugin { activate(ctx: Ctx): void | Promise<void>; deactivate?(): void | Promise<void> }
export const definePlugin = (p: Plugin) => p;
export type Dispose = () => void;
```

### 5.1. Команды

```ts
commands: {
  on(id: string, run: (arg?: unknown) => void | Promise<void>): Dispose; // id из манифеста
  run(id: string, arg?: unknown): Promise<void>;                          // своя или команда ядра из списка ниже
}
```

`run` вызывает команды ядра из открытого списка. Начинаем с минимума: `file.open` (открыть файл), `heading.reveal` (показать заголовок), `agenda.open` (открыть агенду). Список растёт по нуждам наших плагинов: в публичный доступ API пока не идёт.

### 5.2. Интерфейс

```ts
ui: {
  navSection(id: string, render: Render): Dispose;                       // id из манифеста
  view<S>(id: string, spec: { title(state: S): string; crumbs?(state: S): string[]; render: Render<S>; restore?(raw: unknown): S }): Dispose;
  open<S>(viewId: string, state: S, where?: 'here' | 'beside'): Promise<void>;
  form(spec: FormSpec): Promise<Values | null>;                          // лист ядра; поля — те же, что в схеме настроек
  pickPlace(o?: { kind?: 'file' | 'heading'; levels?: number[]; title?: string }): Promise<HeadingRef | { path: string } | null>;
  pickDate(o?: { initial?: Date; title?: string }): Promise<Date | null>;
  review(spec: ReviewSpec): Promise<ReviewResult>;                       // вкладка разбора карточками (0.4)
  notify(text: string, actions?: { label: string; run(): void }[]): void;
}
type Render<S = void> = (el: HTMLElement, state: S, tab: { id: string; setState(s: S): void }) => Dispose | void;
```

- `view.render` получает пустой элемент во вкладке и её ручку: `tab.setState(s)` меняет состояние вкладки, оно сохраняется с раскладкой. `ctx` плагин держит у себя в замыкании, поэтому третьим аргументом идёт вкладка (уточнено в 1.1). Тема (`--p-*`, `--ed-*`, `data-appearance`) доступна через CSS-переменные.
- `review`: `ReviewSpec = { title; items: HeadingRef[]; actions: { id; label; command?; run(h): Promise<'next' | 'stay'> }[]; header?(h): string; below?: Render<HeadingRef> }`. Клавиши действия — у команды манифеста с `"scope": "review"` (она работает, пока показана вкладка разбора, и видна в «Клавишах»), действие ссылается на неё полем `command`. Карточка, суженный редактор, «Назад», «Пропустить», сводка и клавиши остаются за ядром. Действия правят файлы через `edit.transaction`, поэтому ⌘Z работает как везде. Результат — `{ total, done, finished }`, когда очередь пройдена или вкладку закрыли (уточнено в 1.1).
- `pickPlace` — это `PlacePicker` из 0.5, вид «палитра».
- `form`: `FormSpec = { title; groups: Group[]; submit: string; initial?: Values; validate?(v): string | null }`. `validate` возвращает причину, по которой значения не принять: лист остаётся и показывает её (уточнено в 1.1). Поля описываются той же схемой, что в настройках (0.6). Поле ↔ подзаголовок 4-го уровня (из брифа) в v1 не делаем: плагин сам пишет подзаголовки транзакцией. Вернёмся после пилота.
- Декорации редактора — в v1.1 (см. роадмап 3.3).

### 5.3. Индекс (право `index.read`)

```ts
index: {
  query(q: Query): Promise<HeadingInfo[]>;              // тот же движок, что у агенды
  heading(ref: HeadingRef): Promise<HeadingInfo | null>;
  outline(path: string): Promise<HeadingInfo[]>;        // заголовки файла по порядку
  files(): Promise<{ path: string; title: string }[]>;
}
type Query = { sources?: string[]; conds: Cond[]; sort?: Sort };   // условия конструктора агенды (05)
interface HeadingInfo {
  ref: HeadingRef; level: number; keyword: string | null; done: boolean; set: string | null;
  title: string; priority: string | null; tags: string[]; ownTags: string[];
  scheduled?: OrgDate; deadline?: OrgDate; closed?: OrgDate; properties: Record<string, string>;
}
```

### 5.4. Файлы (`files.read`, `files.edit`)

```ts
files: { read(path: string): Promise<string> }          // только внутри рабочей папки, только .org
edit: {
  transaction(label: string, build: (tx: Tx) => void): Promise<'ok' | 'conflict' | 'error'>;
}
interface Tx {
  setStatus(h: HeadingRef, kw: string | null): void;
  setPlanning(h: HeadingRef, kind: 'SCHEDULED' | 'DEADLINE', d: Date | null): void;
  setTags(h: HeadingRef, tags: string[]): void;
  setProperty(h: HeadingRef, key: string, value: string | null): void;
  insertHeading(at: { under: HeadingRef; position: 'first' | 'last' } | { file: string; position: 'top' | 'end' }, org: string): void;
  replaceBody(h: HeadingRef, org: string): void;
  move(h: HeadingRef, to: { under: HeadingRef } | { file: string }): void;
  remove(h: HeadingRef): void;
}
```

- Это `Tx` из 0.1 плюс недостающие операции: `setProperty`, `insertHeading`, `replaceBody`, `move`.
- Шаг журнала подписан `label`, ⌘Z отменяет его целиком.
- `HeadingRef` сверяется по заголовку. Если заголовок не нашёлся, транзакция не применяется и возвращает `'conflict'`.
- Записи «строкой в файл» у API нет. Новый файл создаёт `insertHeading({ file, position: 'top' })` по несуществующему пути внутри папки.

### 5.5. Хранилище

```ts
storage: { folder: Store; local: Store }   // .orgnotes/plugins/<id>.json и «этот Mac» (0.6)
interface Store { get<T>(): T | undefined; set<T>(v: T): Promise<void>; onChange(fn: () => void): Dispose }
```

Права не нужны: плагин видит только своё.

### 5.6. События

```ts
events: { on(e: 'file.changed' | 'heading.changed' | 'tab.active' | 'day.changed' | 'theme.changed' | 'folder.changed', fn: (p: unknown) => void): Dispose }
```

- `file.changed { path, by: 'edit' | 'disk' }` — после записи или чтения с диска.
- `heading.changed { ref, what: 'status' | 'planning' | 'tags' | 'moved' | 'removed' }` — только для правок транзакциями. Ручной ввод в редакторе даёт `file.changed`.
- `day.changed` — в полночь и после пробуждения Mac.

### 5.7. Настройки

```ts
settings: {
  values(): Values; onChange(fn: (v: Values) => void): Dispose;
  dynamic(key: string, spec: { options?(v: Values): Opt[]; hint?(v: Values): string }): Dispose;
}
```

Поля объявлены в манифесте, у каждого поля указано `where`. Значения лежат в хранилищах п. 5.5 под ключом `settings`.

### 5.8. Буфер обмена и сеть

```ts
clipboard?: { write(text: string): Promise<void> };                                   // право clipboard
net?: { fetch(url: string, init?: { method?; headers?; body?: string }): Promise<{ status; headers; text: string }> }; // право net
```

Поле есть в `ctx`, только если право объявлено в манифесте.

## 6. Права (задача 1.3)

### 6.1. Проверка

- В API: без права поля `ctx` нет. Прямой вызов внутренней функции падает с понятной ошибкой «Плагин „Привет“: нужно право files.edit».
- В Rust: команды `net_fetch`, `read_plugin_file` и будущие `process_*` принимают `plugin_id` и проверяют права и хосты по манифесту, который прочитал сам Rust, а не по данным из окна.

### 6.2. Сеть

- В `tauri.conf.json` сейчас `"csp": null`. Включаем CSP: `default-src 'self'`, `connect-src ipc: http://ipc.localhost`, `img-src 'self' data: blob: asset:`, `style-src 'self' 'unsafe-inline'`, `script-src 'self' plugin:`.
- Прямой `fetch` из окна к внешним хостам блокируется.
- `net_fetch` в Rust пускает только к хостам из `net` манифеста. Ответ ограничен 10 МБ, таймаут 30 с.
- Запрос делает системный `/usr/bin/curl`: TLS и прокси macOS, без новых зависимостей в Rust. Манифест Rust читает сам: встроенные — из сборки, установленные — из папки плагина (уточнено в 1.3).
- CSP задан и в `tauri.conf.json` (`csp`, `devCsp` — с websocket для горячей перезагрузки), и meta-тегом в `index.html`, чтобы правило действовало и в dev, и в e2e.

### 6.3. Что закрыто для всех плагинов

- Клавиши ⌘S, ⌘W, ⌘Q, ⌘, и ⌘Z.
- Чтение вне рабочей папки.
- Чужое хранилище.
- Наборы статусов ядра (проекта): плагин добавляет только свои.
- Изменение формата Org.

## 7. «Настройки → Плагины» (задача 1.2)

### 7.1. Раздел

Новый раздел после «Клавиш», с иконкой пазла. В нём два списка: «Встроенные» и «Установленные».

Строка плагина:
- имя, версия, описание, автор;
- права значками;
- переключатель;
- для встроенных — пометка «встроенный»;
- если не включается — причина: «нужно API 2, в приложении 1», «ошибка в манифесте: …», «выключен после ошибки: …» и «Подробнее».

Внизу:
- «Открыть папку плагинов» — Finder;
- «Перезагрузить плагины».

Кнопки удаления нет: сторонний плагин удаляется из папки.

### 7.2. Включение стороннего плагина

Первое включение спрашивает подтверждение листом:

«Плагин „Jira“ получит доступ: чтение заметок, правка заметок, сеть (jira.company.ru). Плагин работает внутри приложения: права защищают от ошибок, но не от намеренно вредного кода. Включайте плагины только из источников, которым доверяете.» Кнопки «Включить» и «Отмена».

Встроенные включаются без вопроса. Согласие запоминается на этом Mac вместе с правами. Если новая версия плагина просит другие права, при запуске он выключается с заметкой «Права плагина изменились — включите его снова» (уточнено в 1.3).

### 7.3. Где хранится

- Список включённых плагинов — на этом Mac, в настройках приложения, как клавиши.
- Встроенные включены по умолчанию.
- Сторонние по умолчанию выключены.

## 8. Наборы тем — плагин-данные (задача 1.4)

- Встроенные темы, кроме Panopticon светлой и тёмной, переезжают в `src/plugins/theme-pack/`. Это `manifest.json` с `contributes.themes` и JSON тем, без `main`.
- Выключили набор — его темы пропадают из выбора, выбранная тема откатывается на Panopticon того же оформления.
- Свои темы пользователя (`themes/`) остаются в ядре.

## 9. Пример: плагин «Привет» (задача 1.1)

`src/plugins/hello/` — тестовый встроенный плагин. В выпуске он выключен по умолчанию; e2e включает его через хранилище. Плагин:
- добавляет команду «Привет: поздороваться» (⌃⌘H). Она показывает уведомление с числом задач из `index.query`;
- добавляет раздел навигатора «Привет» со списком файлов;
- добавляет вид-вкладку «Доска», где показано состояние и есть кнопка, которая транзакцией ставит DONE первой задаче (⌘Z её отменяет);
- добавляет настройку в своём разделе.

## Чего нет в v1

- Изоляции кода (iframe или Worker), защиты от зависаний — это v2.
- Каталога, обновлений, подписи плагинов.
- Своих Rust-частей у плагинов.
- Декораций редактора — это v1.1, по нужде календаря.
- Форм с полем ↔ подзаголовком.
- Права `process` — придёт с терминалом (4.1).

## Решения

2026-10-12, по вопросам черновика.

1. **Граница — vitest-тестом**, без ESLint.
2. **Команды ядра для `commands.run`** — минимум: открыть файл, показать заголовок, открыть агенду. Расширяем по мере наших плагинов, в паблик API пока не идёт.
3. **Формы с полем ↔ подзаголовком** — после пилота.
4. **Папка плагинов — в настройках приложения на этом Mac:** `~/Library/Application Support/dev.local.panopticon/plugins/`, рядом с `themes/`.
   - Сложностей с установкой нет. Папка скрыта в `~/Library`, но кнопка «Открыть папку плагинов» в «Настройки → Плагины» открывает её в Finder: остаётся перетащить туда папку плагина.
   - Почему не как в Obsidian (в рабочей папке): у нас одна рабочая папка за раз, и привязка плагинов к ней мало что даёт. Зато чужая папка заметок приносила бы с собой чужой код. Obsidian для этого держит «безопасный режим», нам он пока не нужен.
   - Настройки плагина, которые описывают файлы, и так едут с папкой (`.orgnotes/plugins/<id>.json`, 0.6).
   - Если понадобятся плагины «для этой папки», добавим второе место поиска позже, с подтверждением при открытии папки.
5. **«Привет» — в сборке, выключенным**, как пример для авторов.
6. **Выпуск с этапом 1 — 1.0.0.** API v1 тоже `1.0.0`; до M2 его можно менять без мажора, сторонних плагинов ещё нет.
