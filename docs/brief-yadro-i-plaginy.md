# Бриф: ядро и система плагинов

2026-10-12 · Yury Bogdanov

## Зачем

Panopticon хочется со временем выложить публично. Ценность таких инструментов — в настройке под себя, как в Obsidian и Emacs. Кроме того, есть сценарии для внутренних нужд компании, которые не должны попасть ни в ядро, ни в публичный репозиторий. Обе задачи решает система плагинов.

Этот бриф — не ТЗ на реализацию, а вход для обсуждения архитектуры. От тебя нужно предложение: как устроить API и в каком порядке переносить функции (см. «Что нужно от тебя»).

Макеты: холст «Panopticon — ядро и плагины» (доски «Принцип», «Карта функционала», «Точки расширения», «Цели квартала как плагин», «Вопросы к разработчику»).

## Принцип

**Ядро даёт возможности, плагины — сценарии.** Ядро отвечает за файлы, Org-модель и общие механизмы интерфейса. Всё, что описывает «как именно я работаю», — плагин.

Проверка одной фразой: *выключили функцию — файлы целы, обычный Org работает как прежде?* Да → плагин. Нет → ядро.

Правила:

1. **Формат и целостность файлов — ядро.** Чтение и запись .org, разбор, сохранение, конфликты с диском, отмена. Плагин никогда не пишет в файл сам — только через ядро.
2. **Общая инфраструктура — ядро с публичным API.** Механизм, нужный двум и более функциям (палитра, клавиши, листы, индекс заголовков, выбор «файл + заголовок», разбор карточками), живёт в ядре и открыт плагинам.
3. **Стандартный Org — ядро.** То, что любой пользователь Org ждёт из коробки и что совпадает с Emacs: статусы, даты, теги, агенда, перенос, поиск, свёртка, быстрый ввод.
4. **Методология и свои соглашения о структуре файла — плагин.** Разбор Inbox, квартальные цели, ревью, шаблоны.
5. **Внешний мир и корпоративное — только плагин.** Сеть, сторонние сервисы, внутренние процессы компании. Корпоративные плагины ставятся локально и не публикуются.
6. **Встроенные плагины пишем строго на публичном API.** Не хватило API — добавляем в ядро точку расширения, а функция остаётся плагином. Обходов через внутренние модули нет.

Порядок решения для новой функции:

- меняет формат файла, сохранение или разбор Org? → ядро;
- нужна двум и более функциям как общий механизм? → ядро + API, сама функция поверх — часто плагин;
- стандартное поведение Org? → ядро;
- иначе — плагин: **встроенный**, если нужен почти каждому с первого дня (идёт с приложением, включён по умолчанию, выключается в настройках); **отдельный**, если нет (ставится по желанию).

## Карта текущего функционала

**Ядро:**

- файлы и хранение — рабочая папка (06), сохранение и изменения на диске (07), закрытие несохранённой вкладки (10), отмена;
- Org-модель — разбор и индекс заголовков, статусы (15), теги, даты, повторы, свойства, drawers;
- редактор — структурный вид и уровни (04), сворачивание drawers (17), движок оформленного текста (19), поиск (21), выделение и текущая строка (fix);
- оболочка окна — вкладки и две панели (11, 13, 14), навигатор как контейнер разделов, дерево и структура (02, 08), строка пути (03, 12);
- команды — палитра (09), клавиши (22), выбор даты (20), перенос (16), быстрый ввод (часть 01);
- общие компоненты — лист настроек со схемой разделов (22), оформление и движок тем (25), листы, диалоги, уведомления, **разбор карточками** (вынести из 18), **выбор «файл + заголовок»** (из 16 и 23);
- агенда — движок запросов и конструктор (05).

**Встроенные плагины:** Inbox как раздел и файл входящих (01), разбор Inbox (18), календарь (24), терминал, наборы тем (25 — плагин только с данными, JSON тем).

**Отдельные плагины:** цели квартала (23) — первый кандидат и пилот API; корпоративные плагины; идеи для сообщества — упоминания @, экспорт, интеграции, шаблоны записей.

Спорные места, которые я решил так:

- Inbox делится: быстрый ввод — стандартный Org (ядро), разбор входящих — методология (плагин).
- Календарь — плагин, хотя агенда в ядре: он показывает те же данные по-другому.

## Точки расширения (минимум для v1)

Список — минимум, нужный для целей квартала и встроенных плагинов. Дальше растёт только по реальной потребности.

**Интерфейс:**

- команды и клавиши — попадают в палитру и в «Настройки → Клавиши», конфликты сочетаний показывает ядро;
- раздел навигатора;
- вкладка-вид — своё содержимое во вкладке редактора;
- лист или диалог на общих компонентах (формы, выбор даты, выбор «файл + заголовок»);
- раздел настроек по схеме — плагин описывает поля, лист рисует ядро;
- действия на карточке общего компонента разбора;
- декорации редактора — подсветка, значки на полях, маркеры без правки файла.

**Данные:**

- запрос к индексу — те же запросы, что у агенды;
- чтение файлов — только внутри рабочей папки;
- правки транзакциями — плагин описывает изменение, ядро применяет его: сохранение, конфликты, ⌘Z работают как для ручной правки;
- регистрация Org-сущностей — наборы статусов, теги, свойства;
- хранилище плагина — настройки и состояние отдельно от .org.

**События:** файл изменён (своей правкой или на диске), заголовок изменён (статус, дата, тег, перенос), файл открыт / вкладка активна, новый день, тема сменилась.

**Гарантии ядра:**

- права в манифесте: чтение, правки, сеть, буфер обмена, процессы; без права вызов не проходит;
- сбой плагина не роняет приложение — уведомление и выключение плагина;
- выключение безопасно — файлы остаются обычным Org и открываются в Emacs;
- плагин объявляет совместимую версию API.

**Плагин не может:** писать в файл в обход транзакций; менять формат Org или вводить синтаксис, который не поймёт Emacs; перехватывать ⌘S, ⌘W, ⌘Q, ⌘,; читать вне рабочей папки и ходить в сеть без права; трогать чужие плагины и внутренние модули ядра.

Набросок манифеста (формат — на твоё усмотрение):

```json
{
  "id": "quarter-goals",
  "name": "Цели квартала",
  "version": "1.0.0",
  "apiVersion": "1",
  "permissions": ["index.read", "files.edit", "clipboard"],
  "contributes": {
    "commands": ["goals.open", "goals.new", "goals.review"],
    "navSection": "goals",
    "views": ["goals.overview", "goals.review"],
    "settings": "settings.schema.json",
    "statusSets": ["BACKLOG ACTIVE | COMPLETED"]
  }
}
```

## Пилот: цели квартала (ТЗ 23)

Цели — первый плагин. Задача пилота — проверить API на настоящей функции: всё, что не ложится на точки расширения, становится доработкой ядра, а не исключением для плагина.

| Функция из ТЗ 23 | Точка расширения |
|---|---|
| Раздел «Цели» в навигаторе, ⌃⌘4 | раздел навигатора, команда + клавиша |
| «Добавить ещё цели»: файл + заголовок 1-го уровня | лист, выбор «файл + заголовок», хранилище плагина |
| Новая цель с полями | лист с формой, транзакция правок |
| Обзор и «Мои цели» по кварталам | вкладка-вид, запрос к индексу |
| Разбор 1-1 по карточкам | разбор карточками, суженный редактор |
| Отметки | транзакция правок |
| «Молчит 14 дней» | запрос к индексу, событие «новый день» |
| Отчёт за квартал в буфер | лист, право clipboard |
| Настройки: порог, источники | раздел настроек по схеме |
| Статусы BACKLOG / ACTIVE / COMPLETED | регистрация набора статусов |

**Что вынести в ядро до переноса** (пригодится и Inbox, и будущим плагинам):

- общий компонент разбора карточками — сейчас он внутри Inbox (18);
- суженный редактор как API — показать один заголовок с потомками;
- формы с org-полями — поле ↔ подзаголовок 4-го уровня;
- выбор «файл + заголовок» — сейчас только в переносе (16);
- хранилище и схема настроек плагина — сейчас настройки целей лежат в общем конфиге.

Поведение целей для пользователя после переноса не меняется. Файловая структура остаётся той же (`* Квартальные задачи / ** Квартал Q4 2026 / *** Цель / **** поля`): выключили плагин — файл открывается в редакторе и в Emacs как обычный Org.

## Вопросы к тебе

1. **Где выполняется код плагина.** JS/TS прямо в webview рядом с интерфейсом — просто, но без изоляции. Или iframe / Web Worker с обменом сообщениями — безопаснее, но дороже. Что берём для v1?
2. **Доступ к Rust и сети.** Только через команды ядра, которые проверяют права из манифеста? Нужны ли плагинам свои Rust-части или запрещаем?
3. **Установка.** Предлагаю для начала папку `plugins/` в настройках приложения: положил — включил. Каталог и обновления — потом. Корпоративные плагины ставятся так же.
4. **Версия API.** Semver для API и `minAppVersion` в манифесте. Что делаем с несовместимым плагином — выключаем с уведомлением?
5. **Где хранить настройки плагина.** На этом Mac или в рабочей папке (`.orgnotes/plugins/<id>.json`), чтобы ехали вместе с файлами?
6. **Порядок переноса.** Мой вариант: 1) API и общие компоненты; 2) цели квартала — пилот; 3) Inbox, разбор, календарь, терминал, темы. Реально ли так, и сколько стоит каждый шаг?
